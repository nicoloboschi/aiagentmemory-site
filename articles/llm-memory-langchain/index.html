LangChain Memory in 2026: What Replaced Buffer Memory

April 6, 2026 7 min read
LangChainLangGraphconversation memoryagent memory

How LLM memory works in LangChain 1.x: ConversationBufferMemory is deprecated, so use LangGraph checkpointers for chat history and stores for long-term memory.

LLM memory in LangChain now means two LangGraph features: a checkpointer that saves each conversation thread’s messages, and a store that keeps facts across threads. The old memory classes, such as ConversationBufferMemory, are deprecated. In LangChain 1.x they survive only in the langchain-classic compatibility package.

Most LangChain memory tutorials online predate that change. This page explains what the current LangChain docs recommend as of October 2026 (langchain 1.4, langgraph 1.2), how each old class maps to the new approach, and working Python for both kinds of memory.

What is LangChain memory?

LangChain memory is the state an LLM application keeps between calls so the model can use earlier turns and known facts. In LangChain 1.x it is built on LangGraph persistence: checkpointers save per-thread conversation state, and stores save JSON documents that any thread can read.

An LLM is stateless. Every call sees only the tokens you send. “Memory” is whatever your code saves and sends back. LangChain splits that job in two:

Short-term memoryLong-term memory
ScopeOne conversation threadAcross threads and sessions
LangGraph featureCheckpointerStore (BaseStore)
Keyed bythread_idNamespace tuple + key
Typical contentMessage history, agent stateUser profile, preferences, facts
Dev backendInMemorySaverInMemoryStore
Production backendsPostgres, SQLite, Redis, MongoDBPostgres, Redis

This split matches the general model of short-term memory in AI agents versus durable memory. For the bigger picture, see the guide to AI agent memory.

Is ConversationBufferMemory deprecated?

Yes. The LangChain API reference says: “Deprecated since version 0.3.1. Use langchain.agents.create_agent instead. Will be removed in version 2.0.0.” It adds that agents which need to remember earlier turns should use create_agent with checkpointing or the Store API.

LangChain 1.0 shipped on PyPI on October 17, 2025. Its release notes say legacy functionality “has moved to langchain-classic,” including the old chains. So this still works, but only as a bridge:

1# Legacy: still importable in 2026, deprecated, removal planned for 2.0
2from langchain_classic.memory import ConversationBufferMemory

The same applies to its siblings: ConversationBufferWindowMemory, ConversationTokenBufferMemory, ConversationSummaryMemory, ConversationSummaryBufferMemory and ConversationEntityMemory. LangGraph’s create_react_agent is also deprecated; the LangGraph v1 notes point to LangChain’s create_agent instead.

Short-term memory: checkpointers and thread IDs

A checkpointer saves the agent’s full state after each step, keyed by a thread_id. Call the agent again with the same thread_id and it reloads the history. A new thread_id starts a fresh conversation.

 1from langchain.agents import create_agent
 2from langchain.agents.middleware import SummarizationMiddleware
 3from langgraph.checkpoint.sqlite import SqliteSaver  # pip install langgraph-checkpoint-sqlite
 4
 5with SqliteSaver.from_conn_string("chat.sqlite") as checkpointer:
 6    agent = create_agent(
 7        model="openai:gpt-5.4-mini",
 8        tools=[],
 9        system_prompt="You are a helpful assistant.",
10        checkpointer=checkpointer,
11        # Replaces ConversationSummaryBufferMemory: summarize old turns past 4,000 tokens,
12        # keep the last 20 messages verbatim.
13        middleware=[
14            SummarizationMiddleware(
15                model="openai:gpt-5.4-mini",
16                trigger=("tokens", 4000),
17                keep=("messages", 20),
18            )
19        ],
20    )
21
22    config = {"configurable": {"thread_id": "user-42-chat-1"}}
23    agent.invoke({"messages": [{"role": "user", "content": "Hi, I'm Dana."}]}, config)
24    reply = agent.invoke({"messages": [{"role": "user", "content": "What's my name?"}]}, config)
25    print(reply["messages"][-1].content)
26
27    # Inspect or wipe a thread
28    print(len(agent.get_state(config).values["messages"]))
29    checkpointer.delete_thread("user-42-chat-1")

Backends listed in the LangGraph docs: InMemorySaver (tests only), PostgresSaver from langgraph-checkpoint-postgres, RedisSaver from langgraph-checkpoint-redis, MongoDBSaver from langgraph-checkpoint-mongodb, plus Oracle. SqliteSaver comes from langgraph-checkpoint-sqlite. Database-backed savers need a one-time setup() call to create tables.

Keeping the checkpoint table from growing

A checkpointer saves a new checkpoint after every step and keeps all of them, so a long-lived thread piles up thousands of rows. Until October 2026, PostgresSaver had no supported way to clean that up: it inherited a prune method that just raised NotImplementedError. langgraph-checkpoint-postgres 3.2.0 (14 October 2026) implements it for PostgresSaver and AsyncPostgresSaver:

1checkpointer.prune(["user-42-chat-1"])                     # keep only the latest checkpoint
2checkpointer.prune(["user-42-chat-1"], strategy="delete")  # drop the whole thread

keep_latest (the default) keeps the checkpoint the agent loads next, plus its pending writes and blobs, and deletes everything older, including blobs only old checkpoints used, which the PR says is most of a long thread’s storage. The conversation still works; you lose time travel and forks to older steps. Per the PR: a 6,000-checkpoint thread pruned in 100-200 ms in the author’s local test; it refuses threads that use a DeltaChannel (deleting their history would empty them); two prunes of the same thread at once can fail, and retrying is safe; and Postgres reuses the freed space without shrinking the files (that takes VACUUM FULL or pg_repack). Pruning doesn’t make the model see less: that’s what summarization or trimming is for.

Trimming instead of summarizing

If you’d rather drop old turns than summarize them, the docs show a @before_model middleware that returns RemoveMessage(id=REMOVE_ALL_MESSAGES) followed by the messages to keep. One warning from the docs: the trimmed history must stay valid. Some providers need it to start with a user message, and every tool call needs its tool result. Cutting blindly in the middle of a tool exchange causes API errors. Trim at turn boundaries, or let summarization handle it.

Long-term memory: the LangGraph store

A checkpointer only remembers within one thread. To remember a user across threads, use a store. It holds JSON documents grouped by a namespace tuple (like a folder) and a key (like a file name). Tools reach it through ToolRuntime.

 1from dataclasses import dataclass
 2
 3from langchain.agents import create_agent
 4from langchain.tools import ToolRuntime, tool
 5from langgraph.checkpoint.memory import InMemorySaver
 6from langgraph.store.memory import InMemoryStore
 7
 8
 9@dataclass
10class Context:
11    user_id: str
12
13
14@tool
15def save_preference(preference: str, runtime: ToolRuntime[Context]) -> str:
16    """Save a lasting preference the user states."""
17    runtime.store.put(("prefs", runtime.context.user_id), preference[:40], {"text": preference})
18    return "Saved."
19
20
21@tool
22def get_preferences(runtime: ToolRuntime[Context]) -> str:
23    """List what we know about the user's preferences."""
24    items = runtime.store.search(("prefs", runtime.context.user_id))
25    return "\n".join(i.value["text"] for i in items) or "Nothing saved yet."
26
27
28agent = create_agent(
29    model="openai:gpt-5.4-mini",
30    tools=[save_preference, get_preferences],
31    checkpointer=InMemorySaver(),
32    store=InMemoryStore(),  # use PostgresStore in production
33    context_schema=Context,
34)
35
36agent.invoke(
37    {"messages": [{"role": "user", "content": "I'm vegetarian, remember that."}]},
38    {"configurable": {"thread_id": "t1"}},
39    context=Context(user_id="dana"),
40)
41# A new thread, same user: the store still has the preference
42agent.invoke(
43    {"messages": [{"role": "user", "content": "Suggest a dinner."}]},
44    {"configurable": {"thread_id": "t2"}},
45    context=Context(user_id="dana"),
46)

For semantic search, create the store with an embedding index, such as InMemoryStore(index={"embed": init_embeddings("openai:text-embedding-3-small"), "dims": 1536}), then call store.search(namespace, query="...", limit=3). That replaces VectorStoreRetrieverMemory.

LangMem for extraction and consolidation

Writing every memory tool by hand gets old. LangMem (MIT) is LangChain’s library on top of the store. It provides create_manage_memory_tool and create_search_memory_tool for memory the agent writes during the conversation (“hot path”), and a background manager that extracts and consolidates memories after the fact. Check its age before adopting it: the last PyPI release, 0.0.30, is from October 2025, and its README still uses the deprecated create_react_agent.

When LangChain’s built-in memory is enough

The checkpointer + store pair is a storage layer. It saves what you tell it to and searches by filter or embedding. It doesn’t decide what’s worth remembering, merge duplicates, or handle facts that change over time. You write that logic, or LangMem’s prompts do it.

That’s fine for chat history and a small user profile. It gets harder when an agent needs to answer “what did this user say about pricing last month?” across hundreds of sessions. That’s where dedicated memory services come in. Mem0, Zep, Letta and Hindsight all extract facts from conversations and run their own retrieval; Each makes different choices about graphs, time and hosting.

Hindsight is a good fit for that exact question. Its recall runs time-range and graph search next to semantic and keyword search, and it ships a hindsight-langgraph package with memory tools and graph nodes, so it plugs into the same agent. Everything is MIT and self-hostable on Postgres. The trade-off: every write calls an LLM to extract facts, so it costs more per message than a plain store. Our comparison of open-source memory systems covers them side by side, and Letta vs LangChain memory covers the harness approach.
