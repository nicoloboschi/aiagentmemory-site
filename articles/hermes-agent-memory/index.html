Hermes Agent Memory: Limits, Best Provider and Fixes

April 7, 2026 12 min read
Hermes AgentNous Researchagent memorymemory providers

Hermes Agent remembers with MEMORY.md (2,200 chars) and USER.md (1,375 chars), loaded once per session, plus SQLite session search. Which of its 9 memory providers to pick, by need, and why Hermes forgets.

Hermes Agent memory is two small, agent-curated files plus a searchable history. MEMORY.md (2,200 characters) holds the agent’s own notes and USER.md (1,375 characters) holds your profile. Both load into the system prompt at session start. Older conversations live in SQLite and are searched on demand. One optional external provider can add more.

Hermes Agent is an open-source (MIT) agent from Nous Research that runs in a terminal, the Hermes Agent desktop app or messaging apps (all sharing the same memory) and creates reusable skills from its own experience. This page covers each layer of its memory, the external providers, and what to check when memory seems broken. Details come from the official Hermes memory docs, checked October 2026.

What is Hermes Agent memory?

Hermes Agent memory is a bounded, curated store that persists across sessions. The agent decides what to save, writes short entries into MEMORY.md and USER.md through a memory tool, and Hermes injects both files into the system prompt as a frozen block when each session starts.

The design is small on purpose. Together the two files are about 1,300 tokens, always in context. Everything else (full transcripts, old tasks) stays out of the prompt until the agent searches for it. That split between always-loaded memory and on-demand recall is the same one described in AI agent memory explained.

With profiles, the files sit under ~/.hermes/profiles/<name>/memories/ instead.

MEMORY.md and USER.md

MEMORY.md is for the agent’s working knowledge: environment facts, project conventions, tool quirks and techniques that worked. USER.md is for you: name, role, timezone, communication style, pet peeves and technical level. The docs say to skip trivial facts, things that are easy to look up again, raw data dumps, and anything already in SOUL.md or AGENTS.md.

Entries are separated by §. The injected block has a header showing usage (for example 67%, 1,474 of 2,200 characters), so the model knows how full the store is.

The memory tool

The agent edits memory with one tool and three actions:

  1. add: append a new entry.
  2. replace: find an entry by a unique substring (old_text) and overwrite it.
  3. remove: delete the entry matching old_text.

There’s no read action, since the content is already in the prompt. Exact duplicates are rejected. When a write would go over the limit, the tool returns an error with the current entries, and the agent must send one batch of operations that frees space and adds the new entry. Hermes never compacts memory on its own. The docs suggest consolidating once usage passes 80%.

Every entry is scanned for prompt injection, credential exfiltration, SSH backdoors and invisible Unicode before it’s saved. That matters because memory is a known attack surface; see AI memory injection.

Session search

Past CLI and messaging sessions are stored in ~/.hermes/state.db. The session_search tool runs full-text search (SQLite FTS5) over them and returns raw messages, and the agent can scroll through a found session. hermes sessions list shows them from the CLI. This is Hermes’s answer to “what did we do last month”: not stored in memory, but findable.

One search beats a better summary. The third-party hermes-jev-skills project (about 1,100 GitHub stars in October 2026) measured session handoffs on seven of its own Hermes working sessions, with a 15-question recall exam each. In its scorecard, letting the next session make one session_search call raised recall by 20 to 33 points for every kind of handoff note. A session with no note and one search (56.7%) beat every note read without search. The best note was written from the whole dialogue with a 1,200-word budget: 58.7% recall alone and 75.0% with one search, against 37.5% and 68.3% for the 400-word note it replaced. These are the authors’ own numbers on seven sessions, not an independent benchmark. The practical lesson: make sure a handoff names the old session id so the next session can search it, and don’t prune sessions you may need to find. Their handoff notes also report that on Hermes 0.21, passing query and session_id together made session_search read the session from the top and ignore the query; search by keywords first, then open the hit with around_message_id.

That history is only findable while it exists. By default Hermes keeps every session, and the sessions docs warn that state.db then “grows without bound”, with multi-GB files reported on gateway and cron installs. Auto-prune is off by default (v0.22.3, October 21, 2026, put it back to opt-in):

1sessions:
2  auto_prune: true      # delete ended sessions past retention_days, at startup
3  retention_days: 90    # default

Only ended sessions are deleted, aged from their last activity, and pruning runs at most once a day. If config.yaml has no auto_prune key and the disk holding state.db runs low (under 2 GB free, or under 10% free with less than 20 GB left), Hermes asks once; answer with /autoprune on, /autoprune off or /autoprune later. For one-off cleanup there’s hermes sessions prune --older-than 30 (add --dry-run to preview), and hermes sessions optimize shrinks the file without deleting anything. The catch for memory: a pruned session is gone from session_search, so anything worth keeping past retention_days has to be in MEMORY.md, a skill, or an external provider, which stores its own copy.

Background review and write approval

After a conversation, a background review can update memory and skills. It’s on by default (auxiliary.background_review.enabled), uses the main model unless you set another, and caps input at 75% of the model’s context window (up to 600,000 tokens). If you want to approve writes, set memory.write_approval: true; staged writes then appear under /memory pending and can be approved or rejected.

Configuring Hermes memory

Settings live in ~/.hermes/config.yaml:

1memory:
2  memory_enabled: true
3  user_profile_enabled: true
4  memory_char_limit: 2200
5  user_char_limit: 1375
6  write_approval: false
7  # provider: honcho   # optional external provider

Turning off both memory_enabled and user_profile_enabled removes the memory tool entirely. You can raise the character limits, but every character is paid for on every turn, so bigger isn’t free.

The /journey command (also hermes journey) shows a timeline of skills and memory entries, and hermes journey delete <node> removes one.

External memory providers

Hermes can run one external provider at a time next to the built-in files. When one is active, Hermes prefetches relevant memories before each turn, syncs turns after each response, extracts memories at session end where supported, and mirrors built-in memory writes to it. The memory providers page lists nine as of October 2026:

Providers are moving out of the Hermes tree into their maintainers’ own repositories. Holographic used to ship in-tree; it’s now maintained by itpartypattaya (itpartypattaya/hermes-plugin-holographic) and installs from the plugin catalog with the same name, settings and database. RetainDB and ByteRover leave core on October 15, 2026, and the docs say their standalone repositories are “unmaintained and open for a new maintainer”, with no catalog install command listed. Honcho, OpenViking, Mem0, Hindsight, Holographic and Supermemory install with hermes plugins install <name>; Memori uses its own hermes-memori CLI. Holographic uses holographic reduced representations, explained in holographic memory for AI agents, and Honcho has its own page on Honcho LLM memory.

If a provider you use stops shipping with Hermes, you don’t have to reinstall it by hand. Per the docs, hermes update installs its catalog plugin for every profile that names it (the desktop app does the same on first start), and the provider name, settings, data directory and tools stay the same. If the install can’t happen (offline, declined, or security.allow_lazy_installs: false), Hermes prints the exact hermes plugins install <name> command.

What a provider sees. Hermes hands the provider each turn, the transcript including tool output, recall queries, session-end and pre-compression transcripts, mirrored memory writes, delegation results and the arguments of the provider’s own tools. All of it first passes through the same secret scrub Hermes uses for chat delivery, even with security.redact_secrets: false, so an API key echoed into tool output is masked before the provider stores it. The docs add a limit: credentials with no recognisable shape, such as an arbitrary password, are not detected. If that matters, pick a provider you can self-host.

OpenViking has published a test against Hermes’s own built-in memory. In its May 2026 benchmark post, Hermes scored 33.38% on LoCoMo with native memory and 82.86% with OpenViking, using 34.3% fewer input tokens. Those are OpenViking’s own numbers, without a stated judge model, and they compare against Hermes’s 1,300-token files rather than against other providers. OpenViking’s Hermes setup also offers a Quick Local server or Volcengine’s hosted service, and memories show up only after background extraction finishes; details in OpenViking agent memory.

How these provider plugins install, update and hook into each turn, plus the full list of 67 Memory-shelf entries in the catalog, is covered in Hermes Agent plugins.

Setup is the same for each:

1hermes plugins install honcho   # or mem0, hindsight, supermemory, openviking
2hermes memory setup             # interactive picker and credentials
3hermes memory status            # confirm which provider is active
4hermes memory off               # disable the external provider

Best memory provider for Hermes Agent

There’s no single best one; it depends on what the agent must remember. Hermes’s provider docs don’t recommend one either, but they do say what sets each apart (checked October 28, 2026):

If you needPickWhat Hermes’s docs say sets it apartRuns where
Months of history, with memories merged into conclusionsHindsighthindsight_reflect “provides cross-memory synthesis that no other provider offers”Cloud, embedded Postgres or local server
A model of the user across sessionsHoncho“cross-session user modeling with dialectic reasoning”Cloud or self-hosted
Memory you don’t manage by handMem0Best for “hands-off memory management”: Mem0 does extraction itselfCloud, self-hosted server or in-process
Nothing leaves the machine, no extra servicesHolographicBest for “local-only memory … no external dependencies”Local SQLite
Recalled memories kept out of what gets storedSupermemory“Automatic context fencing” strips recalled memories from captured turnsCloud or self-hosted
A filesystem-style context storeOpenVikingContext database with a filesystem hierarchySelf-hosted or Volcengine cloud
Nothing beyond the two filesNo providerBuilt-in memory is always onLocal files

Pick Honcho if modeling the user is the point, Mem0 or Supermemory for a hosted fact store with little setup, Hindsight if you want memories consolidated into evidence-backed observations plus a reflect call, and Holographic (or Hindsight’s embedded Postgres) if nothing may leave the machine. Avoid starting new setups on RetainDB or ByteRover until someone maintains them again. Mnemosyne, a single-file SQLite memory that Hermes’s docs list as a catalog provider (hermes plugins install mnemosyne), is another local option; see Mnemosyne vs Hindsight. If the built-in files already hold what you need, skip providers entirely; they add LLM calls and a dependency.

Of the nine, Hindsight and Mem0 are the two with published head-to-head numbers. On Mem0’s own comparison page they tie on LongMemEval (94.6 vs 94.4) and LoCoMo (92 vs 92.5), and Hindsight leads on the long-history BEAM test: 73.9 vs 64.1 at 1M tokens and 64.1 vs 48.6 at 10M (all vendor-run). That matters for a Hermes agent that runs for months. Hermes’s own provider docs also say Hindsight’s hindsight_reflect tool “provides cross-memory synthesis that no other provider offers”. Hindsight is MIT with every feature in the self-hosted server, and it can use local models through Ollama, LM Studio or llama.cpp, so it also works when nothing may leave the machine. The trade-off: Hindsight’s server returns more context per retrieval than Mem0 at its own defaults (24K-44K vs under 7K tokens, by Mem0’s measurement). The Hermes plugin caps that at 4,096 tokens per turn (recall_max_tokens) and recalls only consolidated observations by default, per Hindsight’s Hermes integration docs; since Hermes prefetches recall every turn, lower that cap if prompt cost matters. Each retain also calls an LLM, so writes cost more than a local FTS store. Details in Mem0 vs Hindsight.

Hermes memory not working: what to check

Most “Hermes forgot” reports come from a handful of causes:

  1. The snapshot is frozen. Writes save to disk at once but show up in the prompt only next session. Run /new to reload. Messaging gateways (Telegram, Discord) are one long session until you reset them.
  2. The store is full. At 2,200 or 1,375 characters, new adds fail until the agent consolidates. Check usage in the header or open the files.
  3. Memory is disabled. Confirm memory_enabled and user_profile_enabled in config.yaml, and that memory isn’t listed under agent.disabled_toolsets.
  4. Writes are staged. With write_approval: true, nothing lands until you approve it under /memory pending.
  5. Wrong profile. Each profile has its own memory directory.
  6. The detail was never memory. Long task history belongs in session search, so ask the agent to search past sessions. If auto-prune is on, sessions older than retention_days are gone.
  7. Provider problems. Run hermes memory status. Only one provider can be active, and cloud providers need their credentials (RetainDB, for example, reads RETAINDB_API_KEY from ~/.hermes/.env).

Hermes compared with other agents

Hermes’s built-in memory is closest to OpenClaw’s markdown files and Claude Code’s auto memory: plain text, small, loaded at start. It differs in the hard character caps and the frozen snapshot. Hermes can also import memory from other agents. Since v0.22.5 this is the official agent-importers plugin (hermes plugins install agent-importers, then hermes import-agent), and a fresh hermes setup offers it when it finds ~/.openclaw, ~/.claude, ~/.codex or ~/.cursor. OpenClaw’s MEMORY.md, USER.md and daily notes merge into Hermes memory; Claude Code’s CLAUDE.md, Codex’s AGENTS.md and memories/*.md, and Cursor’s rules become entries in MEMORY.md. Every import shows a preview first, and hermes import-agent --sync pulls in later changes (Hermes docs). Check MEMORY.md after a big import: the memory tool caps it at 2,200 characters, and a long CLAUDE.md alone can be bigger than that. For a side-by-side, see OpenClaw vs Hermes Agent memory.
