OpenAI Agents SDK Memory: Sessions and Sandbox Memory

April 8, 2026 6 min read
OpenAI Agents SDKOpenAIagent memorysessions

How memory works in the OpenAI Agents SDK: Sessions for chat history (SQLite, Redis, SQLAlchemy, Conversations API), compaction, and sandbox agent memory files.

OpenAI Agents SDK memory comes in two parts. Sessions store a conversation’s history and replay it on every Runner.run, so the agent remembers earlier turns. Sandbox agent memory distills lessons from past runs into Markdown files the agent reads next time. There’s no built-in store of user facts across sessions.

This page covers both against the Python SDK (openai-agents 0.23, October 2026), using the official Sessions docs. It also clears up a common mix-up with ChatGPT’s own memory features.

What is memory in the OpenAI Agents SDK?

Memory in the OpenAI Agents SDK is the conversation state the runner carries between turns. A Session object loads prior items before each run and saves new items after it, in SQLite, Redis, a SQL database or OpenAI’s Conversations API. Sandbox agents can add a Memory capability that writes reusable lessons to files.

An agent run is stateless by default. If you call Runner.run twice without passing history, the second call knows nothing about the first. The SDK’s running agents docs list four ways to carry state forward:

StrategyWhere history livesBest for
result.to_input_list()Your appSmall loops, full control, any model provider
session=Your storage, managed by the SDKPersistent chat, resumable runs, custom stores
conversation_idOpenAI Conversations APIServer-side conversation shared across services

The last two work only with the OpenAI Responses API. The docs advise picking one strategy per conversation; a session can’t be combined with conversation_id or previous_response_id in the same run.

Sessions: conversation history

A session is a store keyed by a session ID. Pass it on every turn:

 1import asyncio
 2
 3from agents import Agent, Runner, SQLiteSession
 4
 5
 6async def main():
 7    agent = Agent(name="Assistant", instructions="Reply concisely.")
 8    session = SQLiteSession("user-42", "conversations.db")  # omit the path for in-memory
 9
10    await Runner.run(agent, "My name is Dana and I'm vegetarian.", session=session)
11    result = await Runner.run(agent, "Suggest a dinner for me.", session=session)
12    print(result.final_output)
13
14    # Session API
15    print(await session.get_items(limit=4))  # most recent items
16    await session.pop_item()                 # undo the last item
17    # await session.clear_session()          # wipe the conversation
18
19
20asyncio.run(main())

Before each run, the runner prepends the stored items to the new input. After the run, it saves only the new items.

Keeping session history small

Sessions grow forever by default. Long histories cost tokens and eventually overflow the context window. The SDK gives you three controls:

  1. SessionSettings(limit=N) in RunConfig(session_settings=...) loads only the last N items.
  2. session_input_callback in RunConfig lets you rewrite the history list before it goes to the model, for example lambda history, new: history[-10:] + new. Only new items get saved, so pruning doesn’t re-save old ones.
  3. OpenAIResponsesCompactionSession wraps another session and calls the Responses API compact endpoint when history grows. By default it triggers once 10 or more candidate items exist. It works with OpenAI Responses models only.

Cutting history by item count can split a tool call from its result. The compaction wrapper handles that boundary for you; a hand-written callback has to. For the general tradeoffs, see LLM memory compression.

Sandbox agent memory: lessons across runs

The newer sandbox agents (SandboxAgent, which work inside a filesystem and shell) have a separate feature: the Memory capability. The sandbox memory docs say it is distinct from Sessions. It doesn’t replay chat; it distills lessons from earlier runs.

How it works:

  • After each run, the conversation is appended to sessions/<rollout-id>.jsonl in the workspace.
  • When the session closes, a model summarizes each conversation into raw notes (phase 1), then a consolidation agent writes memories/MEMORY.md and a short memories/memory_summary.md (phase 2).
  • At the next run, the summary is injected into the prompt. The agent searches MEMORY.md and opens per-run summaries only when it needs detail.
  • With live_update on (the default), the agent can fix stale entries mid-run.
1from agents.sandbox import SandboxAgent
2from agents.sandbox.capabilities import Filesystem, Memory, Shell
3
4agent = SandboxAgent(
5    name="Repo reviewer",
6    instructions="Inspect the workspace and keep useful lessons for follow-up runs.",
7    capabilities=[Memory(), Filesystem(), Shell()],  # Memory reads need Shell; live updates need Filesystem
8)

The limits are worth knowing. Memory only survives if the sandbox state survives, through a live session, persisted state or a snapshot. A fresh sandbox starts empty. Raw memories are capped (256 by default) and the oldest drop first. Phase 1 drops system, developer and reasoning content and truncates long conversations. This is closer to procedural memory, “how to do the job here,” than to remembering a user.

Long-term user memory with the Agents SDK

For a chat agent that should remember a user next week in a new session, the SDK has nothing built in. Sessions are per session ID and store raw items, not facts. The usual patterns:

  • Reuse a stable session ID per user. Simple, but history grows without bound and old details get trimmed away.
  • Add a memory tool. Give the agent function_tools that write facts to your database and search them. You own extraction and retrieval.
  • Use a memory service. Mem0 documents an Agents SDK integration, and Hindsight ships hindsight-openai-agents, which adds retain, recall and reflect as FunctionTools. These handle fact extraction and search for you.

With Hindsight, a session keeps the current chat and a memory bank per user keeps what lasts across chats:

 1# pip install hindsight-openai-agents
 2from agents import Agent, SQLiteSession
 3from hindsight_client import Hindsight
 4from hindsight_openai_agents import create_hindsight_tools
 5
 6client = Hindsight(base_url="http://localhost:8888")  # self-hosted, or Hindsight Cloud
 7tools = create_hindsight_tools(client=client, bank_id="user-42", max_tokens=2048)
 8# -> hindsight_retain, hindsight_recall, hindsight_reflect
 9
10agent = Agent(
11    name="Assistant",
12    instructions="Recall memories before answering. Retain lasting facts about the user.",
13    tools=tools,
14)
15session = SQLiteSession("user-42-chat-7", "conversations.db")

Why pick it for this job: its open-source server includes graph and temporal recall and background consolidation of facts into observations, and hindsight_reflect returns a reasoned answer over the whole bank instead of raw hits. On the long-history BEAM benchmark it leads Mem0 64.1 to 48.6 at 10M tokens, per Mem0’s own comparison (vendor-run). The limit: it returns more context per recall than Mem0, about 4x by Mem0’s numbers, which is why max_tokens is set above. See Mem0 vs Hindsight.

Not the same as ChatGPT memory

Several searches mix the Agents SDK up with OpenAI’s consumer features. ChatGPT has its own saved memories and chat-history reference, covered in how to find ChatGPT memory. ChatGPT Atlas, OpenAI’s browser launched in October 2025, adds optional “browser memories” that carry context from pages you visit into later chats. You can view, archive or delete them in settings. None of those features are available to agents you build with the SDK. In the SDK, memory is whatever your sessions and tools store.
