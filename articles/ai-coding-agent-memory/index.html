AI Coding Agent Memory: CLAUDE.md, AGENTS.md and More

April 2, 2026 13 min read
coding agentsClaude CodeCodexCursoragent memory

How AI coding agents remember projects: Claude Code CLAUDE.md and auto memory, Codex AGENTS.md and memories, Cursor rules, Copilot Memory, and external memory tools.

AI coding agent memory is how tools like Claude Code, Codex, Cursor and GitHub Copilot carry project knowledge from one session to the next. The main mechanism is a plain instruction file (CLAUDE.md, AGENTS.md or Cursor rules) loaded into every session. Some agents add automatic memory that saves lessons as they work. For more, teams add an external memory server. For Claude Code specifically, see Claude Code memory.

Every session starts with an empty context window, so anything the agent should know about your build, conventions or past mistakes has to be written down somewhere and loaded back. This page compares how the major coding agents do it, from their official docs, checked October 2026.

What is AI coding agent memory?

AI coding agent memory is any information that persists outside the model and gets put back into a coding agent’s context in a later session: instruction files you write, notes the agent writes for itself, indexed past sessions, and facts stored in an external memory service. Without it, the agent rediscovers your repo from scratch every time.

It splits into two kinds, which map to the memory types in AI agent memory explained:

  • Instructions (procedural memory): rules and commands you want followed every time, like “use pnpm” or “run make lint before committing.”
  • Learnings (episodic and semantic memory): things discovered while working, like “the API tests need a local Redis,” or a fix that worked last week.

Instructions belong in version control. Learnings are often machine-local and generated.

Claude Code: CLAUDE.md and auto memory

Claude Code’s memory docs describe two systems, both loaded at session start.

CLAUDE.md files are instructions you write. They stack by scope: a managed policy file for the organization, ~/.claude/CLAUDE.md for you, ./CLAUDE.md or ./.claude/CLAUDE.md for the team, and a gitignored CLAUDE.local.md for your private project notes. Files above the working directory load at launch; those in subdirectories load when Claude opens files there. You can import other files with @path/to/file (up to four hops deep), and split rules into .claude/rules/*.md, optionally scoped with paths: globs so they load only for matching files. The docs recommend keeping each CLAUDE.md under 200 lines.

Auto memory is notes Claude writes itself, in four types: user, feedback, project and reference. They live in ~/.claude/projects/<project>/memory/, shared across worktrees of the same repo, with a MEMORY.md index plus one file per memory. Only the first 200 lines or 25 KB of MEMORY.md load at start; topic files are read on demand. Auto memory is machine-local and not shared across machines. Toggle it in /memory, or set autoMemoryEnabled: false or CLAUDE_CODE_DISABLE_AUTO_MEMORY=1.

The docs stress one limit: CLAUDE.md is context, “not enforced configuration.” To block an action, use a hook or permission rule. For Claude’s chat-app memory, which is separate, see Claude AI long-term memory.

Codex: AGENTS.md and memories

Codex builds an instruction chain from AGENTS.md files. It reads one global file from ~/.codex (AGENTS.override.md if present, else AGENTS.md), then walks from the repo root down to the current directory, taking at most one file per directory. Files concatenate root-first, so closer files win. Combined size stops at project_doc_max_bytes, 32 KiB by default. You can add other file names with project_doc_fallback_filenames in ~/.codex/config.toml.

Codex memories are separate and off by default. Turn them on in settings or with memories = true under [features]. Codex then turns eligible past chats into files under ~/.codex/memories/ in the background, after a chat has been idle, skipping short sessions and redacting secrets. /memories controls whether the current chat uses or produces memories. OpenAI’s docs say to “keep required team guidance in AGENTS.md,” treating memories as a recall layer, not the source of rules that must always apply. Config keys and add-ons are in Codex memory.

Cursor: rules

Cursor’s rules docs list four kinds: project rules as .mdc files in .cursor/rules (version-controlled), user rules in settings, team rules from the dashboard (Team and Enterprise plans, can be enforced), and AGENTS.md in the root or subfolders. Project rules load in one of four modes: always, when the agent judges them relevant from the description, when files matching globs are in context, or only when @-mentioned.

Cursor used to have an automatic Memories feature. On the official forum, a Cursor staff member wrote that “the Memories feature was intentionally removed starting from version 2.1.x,” and suggested running Export memories from the Command Palette and moving the result into Rules.

GitHub Copilot: Copilot Memory

Copilot Memory is in public preview. It stores repository facts (conventions, architecture decisions, build commands) and user preferences. Repository facts come only from users with write access and cite the code that supports them; before using one, Copilot checks those citations against the current branch and drops facts that no longer hold. Entries unused for 28 days are deleted. Memory is shared across Copilot cloud agent, code review, CLI and agentic autofix. It’s on by default for individual plans; organizations need an admin to enable the policy.

Citation checking is the most interesting design here. It addresses the main failure of coding memory: notes that were true once and quietly go stale.

Two scope limits are easy to miss. Code review uses repository facts only, never personal preferences. And GitHub’s docs don’t list any IDE among the surfaces that use Copilot Memory, so in VS Code your persistent context still comes from AGENTS.md, .github/copilot-instructions.md and .github/instructions/*.instructions.md. Full breakdown, including the settings and the /memory commands in Copilot CLI, in GitHub Copilot Memory.

Cline: rules and the Memory Bank

Cline persists instructions through rules files, usually .clinerules/*.md in the repo, or global custom instructions. On top of that sits the Cline Memory Bank, which is not a feature but a block of custom instructions you paste into a rules file. It tells Cline to keep six markdown files in a memory-bank/ folder (projectbrief.md, productContext.md, systemPatterns.md, techContext.md, activeContext.md and progress.md) and to rewrite them when the project changes. Three phrases drive it: “initialize memory bank”, “update memory bank” and “follow your custom instructions”.

The design choice that separates it from everything above: Cline’s Memory Bank docs say the agent “MUST read ALL memory bank files at the start of EVERY task”. There is no retrieval and no size cap, so cost rises with the folder and is paid on every task, including trivial ones. Because it is only markdown plus instructions, the same pattern was copied to Roo Code, Cursor and other agents.

DeepSeek Harness: session log and compaction

DeepSeek Harness (dsh) keeps each session as an append-only event log and compacts older turns into a summary when the context nears the window. Nothing carries over to a new session. Memory across sessions comes from plugins (Hindsight, Honcho, Mem0, ReMe) or default-off MCP overlays; details in DeepSeek Harness memory.

What to put in each layer

A workable split, based on what each vendor’s docs recommend:

  1. Build, test and lint commands go in AGENTS.md or CLAUDE.md. The agent needs them every session.
  2. Hard rules (“never push to main”) go in permissions or hooks, with a reminder in the instruction file.
  3. Path-specific conventions go in scoped rules (.claude/rules/ with paths:, Cursor globs, nested AGENTS.md).
  4. Long procedures go in skills or docs the agent reads on demand, not in always-loaded files.
  5. Personal preferences go in user-level files (~/.claude/CLAUDE.md, user rules, CLAUDE.local.md).
  6. Lessons and gotchas can go to auto memory, then get promoted into the shared file once the team agrees.
  7. Long history (why a decision was made six months ago) belongs in an external memory or searchable session archive.

Keep instruction files short. Everything in them costs tokens on every turn and competes for attention.

Do coding agents need memory or documentation?

Mostly documentation, plus memory for what nobody writes down. Kevin Liao’s post Agents don’t need memory, they need documentation (October 2026, 391 points on Hacker News) argues that most memory plugins mine transcripts into snippets and inject the closest matches by similarity. Closeness isn’t correctness: a snippet can be stale, lose the reason behind a decision, or contradict today’s code, and a vector store is hard to audit. His fix is a maintained docs folder (specs, decisions, constraints) that the agent reads before working and rewrites when facts change, released as the BSD-licensed Operator Memory.

The vendors agree on the rules part: OpenAI’s Codex docs say required team guidance belongs in AGENTS.md, with memories as a recall layer. Where docs fall short is the long tail: the bug that took three sessions to find, or why an option was dropped, which rarely makes it into a spec.

The critique fits append-only snippet stores best. Hindsight addresses part of it: it merges related facts into observations that are refined as new evidence arrives rather than stacked as duplicates, and keeps mental models, standing answers updated in the background. What it doesn’t give you is a file you review in a pull request. A practical split: docs in the repo for anything that must always hold, a memory store for history and lessons, and promote a lesson into the docs once it becomes a rule.

Does reusing past coding sessions help?

Yes, but research says how you store and dose the experience matters more than how well you retrieve it. The REM paper (Chen et al., arXiv, October 19, 2026) tests experience memory on repository-level bug fixing with SWE-ContextBench Lite. REM makes three decisions inside the agent’s loop:

  • What to store. Each finished run is condensed into a document split by work phase, which the authors say is two orders of magnitude smaller than the raw trajectory.
  • When to recall. That document is injected at the start of a related task. The more detailed implementation record is held back until a check inside the loop sees the agent struggling.
  • What to forget. The implementation record is dropped after the agent has seen it once.

On SWE-ContextBench Lite, REM found the related past run 68.7% of the time at match@1, per the REM paper (October 2026). The best of the state-of-the-art memory systems it was compared with scored 55.6% on that retrieval test, per the same paper. REM fixed 27.6% of the bugs on SWE-ContextBench Lite, against 24.9% for the comparison, in every replicate, per the REM paper (October 2026). REM did this at 17% lower cost than the comparison, per the paper’s abstract. The authors report that giving the agent the same experience as a plain summary or as the raw trajectory did not improve resolution, even when the right past run was picked by hand. Removing any one of the three decisions lowered resolution.

The practical lesson for teams: dumping old transcripts into context is not enough. Keep lessons short, load them when a task matches, and hold the full detail back until it is needed. Memory servers that consolidate sessions into compact facts, rather than replaying them, follow the same idea.

Sharing one file across agents

If a team uses several agents, maintain one AGENTS.md. The format is stewarded by the Agentic AI Foundation under the Linux Foundation, and agents.md says it’s used by over 60,000 open-source projects and read by Codex, Cursor, Copilot’s coding agent, Gemini CLI, Jules, Aider, Zed, Windsurf and others.

Claude Code reads AGENTS.md directly when there’s no CLAUDE.md (v2.1.277+). If you want both, put a one-line CLAUDE.md that imports it:

1@AGENTS.md
2
3## Claude-specific
4- Use the Read tool before editing large files.

Moving learned memory between agents

AGENTS.md covers rules you write. What an agent learned on its own is harder to move, because each tool keeps it in its own format:

A one-time import is fine when you switch tools for good. If a team keeps using two agents on the same repo, copies drift apart as soon as either agent learns something new, and only a shared store keeps them in step.

External memory for coding agents

Built-in memory is per machine and per tool. Teams that want lessons shared across developers, agents and months of history add an external store, usually over MCP:

  • Session archives. MemPalace mines Claude Code, Codex and Cursor transcripts into a local verbatim index with auto-save hooks; see MemPalace.
  • Hook-based session capture. claude-mem hooks into the agent’s session lifecycle, compresses tool use into observations with an LLM, and stores them in local SQLite with a Chroma index. At 101,326 GitHub stars on 17 October 2026 it is the most starred of these add-ons, and it installs for OpenCode, Codex via T3 Code and several other harnesses as well as Claude Code; see claude-mem.
  • Code knowledge graphs. Graphify parses the repo with tree-sitter into a graph the agent queries instead of grepping. It remembers the code’s structure, not past sessions; see Graphify.
  • Markdown knowledge bases. Basic Memory keeps notes as Markdown with an SQLite index and exposes them as MCP tools. Operator Memory goes further and argues curated Markdown should replace the memory server outright; that trade-off is laid out in agent memory vs documentation.
  • Extraction-based memory servers. Mem0, Zep and Hindsight store extracted facts. Hindsight ships a coding-agents package (@vectorize-io/hindsight-coding-agents) for per-repo project memory and integrations for Claude Code, Codex, Cursor and others.

Of the extraction-based servers, Hindsight has the most coding-agent coverage: native plugins for Claude Code, Codex, Cursor and Copilot, plus opencode, Cline and Aider integrations and an MCP endpoint per memory bank. Three things matter for a team:

  • It learns, not just stores. Related lessons are merged into observations that keep their supporting quotes and get refined as new sessions add evidence, and reflect answers questions like “why did we drop the Redis cache?” by reasoning over many memories.
  • Long histories. On the BEAM benchmark it scores 73.9 at 1M tokens and 64.1 at 10M, against 64.1 and 48.6 for Mem0’s Platform (Mem0’s own comparison page; vendor-run). Months of coding sessions are exactly that kind of history.
  • Runs on your models. The MIT server includes every feature and works with 25+ LLM providers, local Ollama included, or an existing Claude Code or Codex subscription instead of an API key.

The limit: it returns more context per retrieval than Mem0 by default, so set a lower max_tokens to keep each session’s prompt small.

Each adds a dependency and, for extraction-based tools, LLM calls per write. Start with instruction files; add a server when the same lesson keeps getting lost across people or machines. The options are compared on AI memory MCP servers.

Memory files are also an attack surface. A malicious instruction written into a memory file, or committed in a shared CLAUDE.md, loads into every future session. Claude Code asks for approval before loading imports from outside the repo for that reason. More on the risk in AI memory injection.
