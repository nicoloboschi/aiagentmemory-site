Microsoft Agent Framework Memory: Sessions and Providers

April 8, 2026 12 min read
Microsoft Agent FrameworkSemantic KernelAutoGenagent memory

How memory works in Microsoft Agent Framework (Python 1.25): AgentSession, history and context providers, the Harness Agent's MEMORY.md memory with extraction and consolidation, and Mem0, Foundry, Cosmos DB, Redis, Hindsight compared.

Microsoft Agent Framework memory is built from two pieces. An AgentSession holds one conversation’s state across agent.run calls. Context providers run before and after each call: history providers reload and save the transcript, and memory providers extract and recall lasting facts through Mem0, Redis, Cosmos DB, Neo4j or Microsoft Foundry.

Agent Framework is the successor to Semantic Kernel and AutoGen, built by the same teams. The Python package hit 1.0 in April 2026 and is at 1.25.0 as of 7 November 2026; the October and November releases changed the Redis memory index in a way that needs a re-ingest, dropped Python 3.10 and fixed two bookkeeping bugs in the harness’s file memory. Code below follows the Agent Framework memory tutorial and the package’s current signatures.

What is memory in Microsoft Agent Framework?

Memory in Microsoft Agent Framework is the context an agent carries between runs. An AgentSession groups a conversation and holds shared state. Context providers attached to the agent load that context before each model call and save what happened after it, either as a full transcript (history) or as selected durable facts (memory).

The docs split providers into patterns:

PatternWhat it doesExamples
Conversation storageReloads and saves the exact transcriptInMemoryHistoryProvider, Redis, Cosmos DB
MemoryExtracts and recalls selected durable factsMem0, Foundry, Redis, Neo4j, Cosmos DB
RAGRetrieves from an external knowledge sourceAzure AI Search, Foundry, Neo4j, Redis

This split mirrors the general difference between short-term and long-term memory: one keeps the conversation going, the other remembers the user.

Sessions: multi-turn conversations

Pass the same session to every run and the agent sees earlier turns:

 1import asyncio
 2
 3from agent_framework import Agent, AgentSession
 4from agent_framework.openai import OpenAIChatClient
 5
 6
 7async def main():
 8    agent = Agent(
 9        client=OpenAIChatClient(model="gpt-5.4-mini"),  # reads OPENAI_API_KEY
10        instructions="You are a friendly assistant. Keep answers brief.",
11    )
12    session = agent.create_session()
13
14    await agent.run("My name is Alice and I love hiking.", session=session)
15    print(await agent.run("What do you remember about me?", session=session))
16
17    # Save and restore across processes
18    saved = session.to_dict()  # JSON-serializable dict
19    restored = AgentSession.from_dict(saved)
20    print(await agent.run("And my name?", session=restored))
21
22
23asyncio.run(main())

Where the transcript lives depends on the model service. Services that keep conversation state, such as OpenAI Responses or Foundry, store it server-side and the session holds a service_session_id. Otherwise a local history provider stores it. The Python docs note that the agent may add an InMemoryHistoryProvider automatically in some cases, “but this is not guaranteed,” so add one explicitly if you rely on it.

The session docs flag a security point. Service-side IDs like resp_* or conv_* are scoped to your API key or project, not to your end users. In a multi-user app, map client session IDs to service IDs in your own storage and check ownership before resuming.

History providers: persisting the transcript

InMemoryHistoryProvider keeps the transcript in process memory. For persistence, swap in a database-backed provider, such as Redis from the agent-framework-redis package:

 1from agent_framework import Agent
 2from agent_framework.openai import OpenAIChatClient
 3from agent_framework.redis import RedisHistoryProvider
 4
 5history = RedisHistoryProvider(
 6    source_id="chat_history",
 7    redis_url="redis://localhost:6379",
 8    application_id="support-bot",
 9    agent_id="support-bot",
10    max_messages=50,  # keep the last 50 messages
11)
12
13agent = Agent(
14    client=OpenAIChatClient(),
15    instructions="You are a helpful support assistant.",
16    context_providers=[history],
17)

InMemoryHistoryProvider accepts flags that control what it saves: load_messages, store_inputs, store_outputs and store_context_messages. The docs warn that only one history provider should have load_messages=True, or you’ll replay several transcripts into the same call. A common pattern adds a second provider with load_messages=False, store_context_messages=True as an audit log of everything the model saw.

Context providers: custom and long-term memory

A context provider subclasses ContextProvider and implements before_run and after_run. Before the call it can add instructions, messages or tools. After the call it can save what it learned. Per-session state goes in the state dict, which serializes with the session:

 1from typing import Any
 2
 3from agent_framework import AgentSession, ContextProvider, SessionContext
 4
 5
 6class UserNameMemory(ContextProvider):
 7    def __init__(self) -> None:
 8        super().__init__("user_name_memory")
 9
10    async def before_run(self, *, agent: Any, session: AgentSession,
11                         context: SessionContext, state: dict[str, Any]) -> None:
12        name = state.get("user_name")
13        context.extend_instructions(
14            self.source_id,
15            f"The user's name is {name}." if name else "Ask for the user's name.",
16        )
17
18    async def after_run(self, *, agent: Any, session: AgentSession,
19                        context: SessionContext, state: dict[str, Any]) -> None:
20        for message in context.input_messages:
21            _, found, rest = (message.text or "").lower().partition("my name is")
22            if found and rest.strip():
23                state["user_name"] = rest.split()[0].capitalize()

That example only lasts as long as the session. For memory across sessions, use a provider backed by a memory service:

  • Mem0 (pip install agent-framework-mem0, then from agent_framework.mem0 import Mem0ContextProvider). Set storage scopes (user_id, agent_id, application_id) and retrieval scopes (search_user_id, and so on) separately. The docs warn that if no search_* scope is set, it stores memories but never recalls them.
  • Microsoft Foundry (FoundryMemoryProvider in agent_framework.foundry): managed semantic memory in a Foundry memory store, scoped per user. Our page on Azure AI Foundry long-term memory covers the service side.
  • Azure Cosmos DB memory (pip install agent-framework-azure-cosmos-memory --pre, then from agent_framework_azure_cosmos_memory import CosmosMemoryContextProvider). Built on the Azure Cosmos DB Agent Memory Toolkit, it extracts facts, procedural knowledge and episodic memories from each turn, consolidates a cross-thread user profile, and deduplicates and resolves contradictions, per the package README. One Foundry project endpoint powers both the memory extraction and the agent.
  • Redis (RedisContextProvider, backed by a RedisVL search index) and Neo4j providers, listed on the context provider integrations page.

What changed in the October and November 2026 releases

The October and November 2026 releases mostly hardened these providers rather than adding new ones. One of them breaks existing Redis memory, and the 7 November release closes the door on Python 3.10, per the Agent Framework release notes:

The Redis change. Before 1.24.0, the Redis provider matched scopes through Redis TAG defaults that don’t keep every ID exactly. Per PR #9461, distinct application IDs (for example, ones differing only in case or punctuation) could be treated as the same one, which breaks the isolation the scopes are meant to give. The new schema stores scopes as exact, case-sensitive tokens and enforces the configured scope on every write and search. It refuses to start on an index built by an older version, and overwrite_index=True does not migrate it. To upgrade: delete the old context index and its context hashes, let the provider create the new index, and re-ingest your context data. Plan for this before you bump the package: there is no in-place migration.

The Mem0 fix (.NET). The .NET Mem0Provider already refused empty storage and search scopes, but only when it created fresh state. A session restored from a saved state bag skipped that check. Per PR #9827, with empty restored scopes, clearing stored memories sent a delete request to Mem0 with no scope filter, and storage failures were only logged. From 1.27.0 the search, store and clear paths all run the same scope check and throw instead.

Agent-triggered compaction. Compaction strategies used to run only on rules the developer set, such as a token count. The new AgentTriggeredCompactionStrategy wraps an existing strategy and gives the agent one tool to ask for compaction itself, for example after it finishes planning. The wrapped strategy still decides what is removed. UnloadSkillsCompactionStrategy adds an unload_skill tool that drops loaded skills from the context once the agent is done with them. Neither changes the saved history in sessions or history providers; they only trim what the model sees during the run.

Third-party memory systems also ship providers. Hindsight publishes hindsight-agent-framework, whose HindsightProvider recalls memories in before_run and retains the exchange in after_run, so the model doesn’t have to remember to call a memory tool:

 1# pip install hindsight-agent-framework
 2from agent_framework import Agent
 3from agent_framework.openai import OpenAIChatClient
 4from hindsight_agent_framework import HindsightProvider
 5
 6agent = Agent(
 7    client=OpenAIChatClient(),
 8    instructions="You are a helpful assistant.",
 9    context_providers=[
10        # one bank per user; omit hindsight_api_url to use Hindsight Cloud (HINDSIGHT_API_KEY)
11        HindsightProvider(bank_id="user-123", hindsight_api_url="http://localhost:8888"),
12    ],
13)

Compared with the Mem0 provider, Hindsight’s open-source server includes graph and temporal recall and background consolidation of facts into observations, features Mem0 keeps on its paid Platform. It also leads Mem0 on the long-history BEAM benchmark (64.1 vs 48.6 at 10M tokens, per Mem0’s own comparison; vendor-run). The tradeoff: it injects more context per run than Mem0 by default, so set max_tokens on the provider if prompt size matters. See Mem0 vs Hindsight.

Harness Agent memory

Agent Framework also has a Harness Agent (create_harness_agent in Python): an opinionated agent for long, multi-step tasks with planning, context compaction, file access and memory built in. It uses the same AgentSession lifecycle. Per the docs, the harness saves history after each model call inside a tool loop, not just at the end of a run. Reuse and serialize the session so todos, file memory and tool approvals survive a restart.

Its long-term memory is a MemoryContextProvider, a history provider that also keeps a Markdown memory store. These defaults come from the provider’s source at 1.25.0, read on 9 November 2026; every one is a constructor argument:

PieceDefaultWhat it does
MEMORY.mdUp to 200 pointer lines of 150 characters (index_line_limit, index_line_length)One line per topic: slug, summary, last update. Rebuilt from the topic files before every run
topics/<slug>.mdOne file per topicThe durable memory lines for that topic, plus a summary
transcripts/Saved every runThe conversation history, written by the same provider (FileHistoryProvider underneath)
state.jsonPer ownerConsolidation bookkeeping: last pass time, sessions finished since, pending turn ids
Auto-loaded topics3 (selection_limit)Topic files whose pointer matches keywords in the user’s message are injected with MEMORY.md; 0 turns it off
Recent turns0 (recent_turns)How many recent transcript turns to inject next to durable memory
Extraction5 items per turn (max_extractions)After each run, the agent’s own chat client reads the turn and returns {"memories":[{"topic","memory"}]}: durable facts, preferences, decisions, one sentence each, no “transient tasks … or tool chatter”
Consolidation5 sessions and 24 hours (consolidation_min_sessions, consolidation_interval)Rewrites each topic file “into a tighter durable form”: dedupes, drops stale items, shortens the summary. consolidation_client lets the pass run on a cheaper model
Tools given to the modellist_memory_topics, read_memory_topic, write_memory, delete_memory_topic, search_memory_transcripts, consolidate_memoriesAll run without approval prompts; consolidate_memories forces an immediate pass across all topic files

So the harness follows the same index-plus-topic-files layout as Claude Code’s auto memory (also a 200-line MEMORY.md, see Claude Code memory), with two differences: extraction is a separate model call after every turn rather than the agent writing notes mid-task, and consolidation is scheduled rather than left to the user. The 1.25.0 fixes above matter here. Before #9294, a consolidation pass that started while another session was still extracting cleared that session from the pending list, so its facts were saved but didn’t count toward the next pass and “wait for unrelated sessions before they are consolidated”. And before #9547, a half-written or hand-edited state.json raised JSONDecodeError on every later turn; it is now quarantined next to the original and the store restarts from a clean state. The source also warns that the storage directory must not be writable by untrusted users, since the final memory files could be swapped outside the store’s own atomic writes, the same class of risk covered on memory poisoning in AI agents.

Coming from Semantic Kernel

Microsoft’s Semantic Kernel migration guide maps the conversation pieces directly. Semantic Kernel’s ChatHistoryAgentThread becomes agent.create_session(), and agent.get_session(service_session_id=...) continues a service-managed conversation. There’s no session delete API, since not every provider supports deleting hosted history, so track and delete server-side history through the provider’s own SDK.

Existing Semantic Kernel vector stores aren’t stranded either. With semantic-kernel 1.38 or later, collection.create_search_function(...) returns a kernel function, and .as_agent_framework_tool() turns it into an Agent Framework tool. Support differs by language: Mem0 is Python-only, and the Go SDK, in public preview, has no Harness Agent and none of the listed providers yet.

For how Agent Framework’s approach compares with LangGraph, CrewAI and the OpenAI Agents SDK, see the AI agent framework comparison and the AI agent memory guide.
